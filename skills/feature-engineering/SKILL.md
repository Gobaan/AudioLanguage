# Feature Engineering

## Core Posture

Start from lived situations, not abstractions. Ask what the user is trying to do in the world, what pressure or emotion is present, what feedback they receive, and what changes after the interaction.

Prefer concrete moments over categories:

- A scene, exchange, or task beats a feature label.
- A user's first successful action beats a long tutorial.
- A staged journey beats a static feature inventory.
- A feedback loop beats a one-time assessment.

Use research as a constraint, not decoration. Translate principles into product mechanics and call out where an idea creates false progress, excessive grind, or shallow recognition.

## Workflow

1. Restate the raw idea as a user situation.
2. Identify the real unit of value: exchange, scene, decision, artifact, habit, or outcome.
3. Separate first exposure, guided practice, independent production, review, and maintenance.
4. Design the day-one experience before expanding the system.
5. Map progression over time: first session, next day, one week, one month, long-term use.
6. Add variation so repeated use requires fresh retrieval or decision-making, not pattern matching.
7. Define feedback signals that reveal understanding, confidence, fluency, or transfer.
8. Remove anything that only looks educational, engaging, or useful without changing user capability.

## Useful Lenses

### Context Before Isolation

Embed ideas in meaningful situations before isolating components. For learning products, introduce phrases, concepts, or skills inside a scene or task, then use targeted review for maintenance.

### Reception Before Production

Let users observe or understand enough to form a scaffold, then make them act. Production should happen early, but not before the user has any situational anchor.

### Progressive Slots

Look for reusable structures users can fill over time. A beginner may start with one chunk, then later replace pieces inside it as understanding grows.

### Retrieval Beats Recognition

Prefer prompts that require users to produce, choose under uncertainty, explain, repair, or transfer. Recognition-only interactions often feel good while measuring weak capability.

### Emotional and Situational Salience

Tie ideas to stakes people actually feel: getting unstuck, being understood, helping someone, avoiding embarrassment, completing a transaction, or seeing visible progress.

### i+1 Difficulty

Keep the next step mostly comprehensible with one meaningful stretch. If the user is lost, add context. If the user is cruising, add pressure, variation, or a new constraint.

### Rotate Challenges

Do not repeat the exact same prompt with the exact same answer. Keep the anchor stable while rotating the challenge: identify, produce, repair, compare, infer, transfer, or respond freely.

### Parallel Layers

Avoid hard gates when possible. Let foundational practice and real use run in parallel, with available scenarios or tasks constrained by what the user has already encountered.

## Product Shaping Prompts

Use these questions while brainstorming:

- What can the user do successfully in the first 5-15 minutes?
- What is the smallest authentic version of the target behavior?
- Where does the system create confidence without competence?
- Where does the system ask for recognition when it should ask for production?
- What changes between day one, day seven, month one, and year one?
- What unlocks make practice feel immediately useful?
- What weak signals should feed back into the next session?
- What should become easier, faster, more natural, or more automatic over time?
- What is the maintenance mode after the user no longer needs the beginner experience?

## Output Shape

For open-ended feature work, produce a concise but concrete concept:

- Core idea in one paragraph
- First user session
- Progression over time
- Key mechanics
- Feedback loop
- Risks or failure modes
- Smallest buildable version

When comparing options, prefer a decision table or ranked list with tradeoffs tied to user capability, motivation, cost, and implementation risk.

## Failure Checks

Before finalizing an idea, check for:

- **Flashcard trap**: isolated recall replaces contextual use.
- **Tutorial trap**: explanation delays the first meaningful action.
- **Gamification trap**: users optimize points instead of capability.
- **Content trap**: more material is treated as progress without better sequencing.
- **Synthetic trust gap**: generated content is plausible but culturally, emotionally, or practically wrong.
- **Measurement gap**: the metric tracks completion, not understanding or transfer.
- **Grind leak**: review volume grows without a visible payoff.
